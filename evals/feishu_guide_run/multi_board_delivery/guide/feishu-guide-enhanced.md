## 技能简介

`skill-creator-pro` 是一个适配多 Agent 的单包 Skill 自动开发器。它把需求澄清、计划、开发、测试、评审、飞书图文指南、默认介绍画板与 Agent 安装包打包整合进一个技能目录里，目标是让用户只安装这一个技能，就能完成从需求描述到 skill 交付的闭环。

### 为什么需要它

在没有这个技能之前，用户通常需要分别依赖 `brainstorming`、`superpowers`、`skill-creator`、`lark-doc`、`lark-whiteboard`、`design-lark-chart` 等多个技能：前面一个负责澄清，后面一个负责计划，再换一个负责打包，再切到飞书文档和画板相关技能继续做落地。这种方式虽然单点能力强，但在真实使用中会带来明显割裂：

- 需要记住多个技能的触发方式和边界
- 需求澄清、计划、开发、验证、交付之间缺少统一主链路
- 飞书指南、画板和 Agent 安装包打包往往落在不同工具链里，容易中断
- 很多能力虽然都存在，但无法在一次任务里自然衔接

## 当前技能实际集成了哪些能力

为了让用户只安装这一个 skill 就能走完整条交付链路，当前版本已经把以下关键能力内聚到同一套流程里：

- **需求澄清 / 设计前置**：吸收 `brainstorming` 的核心思路，先确认目标、约束、验收标准，再进入开发。
- **计划 / 执行 / 验证骨架**：吸收 `superpowers` 与 `planning-with-files` 的方法，维护 `task_plan`、`findings`、`progress`，并保留 Gate 1 / Gate 2。
- **Skill 开发与交付**：吸收 `skill-creator` 与 `find-skills` 的能力，用于结构生成、复用判断、校验与 Agent 安装包打包。
- **飞书文档 / 画板 / 图表落地**：吸收 `lark-doc`、`lark-whiteboard`、`design-lark-chart` 的核心工作流，用于指南生成、画板插入与图表交付。
- **Lark 深水区补位**：吸收 `lark-openapi-explorer` 与 `lark-skill-maker` 的能力，在现成 CLI / skill 不够用时继续向原生 OpenAPI 和新 skill 规格扩展。

这也是当前 skill 与“临时拼装多个 skill”的根本差异：**它不是简单引用外部提示词，而是把高频能力收束进一个面向交付的统一主链路里。**

## 适用场景

- 把重复工作沉淀成可复用 skill
- 希望自动完成需求澄清、计划、开发、测试、评审与打包
- 希望最终自动产出飞书使用指南和介绍画板
- 不想额外安装 brainstorming、superpowers、lark-doc、design-lark-chart 等多个技能

## 触发方式

- 帮我做一个 skill
- 把这个流程沉淀成技能
- 帮我自动生成 Agent 可安装 skill
- 帮我给 skill 生成飞书指南和画板

## 输入 / 输出

### 输入
- 自然语言需求描述
- 可选的已有 skill/脚本/参考资料
- 可选的飞书文档目标位置

### 输出
- 可安装的 skill 目录
- Agent 兼容安装包
- 测试/评审/安全摘要
- 飞书使用指南
- 默认介绍画板与文档插入计划

## 使用步骤

1. 生成显式需求澄清摘要，确认目标 / 输入 / 输出 / 约束 / 验收标准
2. 检索可复用 skill 与参考资料，判断 simple / complex
3. 创建 `task_plan / findings / progress`，并停在 Gate 1 等待确认
4. 用户确认后进入开发与验证，持续更新执行状态与证据
5. 汇总测试、评审、安全摘要，并停在 Gate 2 等待验收
6. 用户验收通过后，生成飞书使用指南、画板与命令计划
7. 完成 Agent 安装包打包，输出 zip 与安装清单

### 这条流程解决了什么问题

这条流程的核心价值，不只是“自动生成一个 skill”，而是把原本散落在多个 skill 和多个阶段里的能力串成统一流水线：

- 前面先澄清，不再一上来就直接开发
- 中间有 Gate 1 / Gate 2，不再无确认推进
- 后面自动补齐飞书文档、画板与打包，不再临近交付时再手工拼凑
- 如果涉及 Lark/OpenAPI 或图表能力，也优先复用内置子系统，而不是再跳到别的 skill 里重新组织

## 真实调用案例

下面建议补充两个真实调用案例，帮助读者理解这个 skill 在不同输入条件下会如何推进任务。

### 案例 1：信息相对完整时，快速进入计划确认

这个案例展示的是：当用户一开始就已经把技能目标、流程、模块划分、图表类型推断和插入策略描述得比较完整时，当前 skill 会更快地进入结构化规划，并输出相对完整的计划确认内容。

从该案例可以看出，skill 会：

- 先给出清晰的技能名称与核心功能流程
- 把模块拆成文档下载、结构分析、画板生成、画板插入等明确子模块
- 自动总结图表类型推断逻辑
- 给出插入位置策略和默认行为
- 在正式开发前停在 Gate 1，等待用户确认方案

这个案例说明：**当输入已经比较完整时，当前 skill 的优势是快速把零散描述整理成结构化方案，并在确认后直接进入交付链路。**

### 案例 2：信息不完整时，先补充关键澄清

这个案例展示的是：当用户只给出一个方向性的目标，例如“要能读飞书文档、补图、最后生成指南并打包”，但很多关键决策尚未明确时，当前 skill 不会直接进入开发，而是先发起一轮结构化澄清。

从该案例可以看出，skill 会主动追问：

- 读文档的范围到底是什么
- 补图的具体形式是什么
- 最终产物偏向飞书文档、Markdown 还是两者都要
- 触发方式是临时调用、固定 skill，还是模板化复用
- 验收标准是什么

在用户补充完这些关键约束后，skill 才会整理为新的计划确认版本，并再次停在 Gate 1 等待确认。

这个案例说明：**当前 skill 的一个关键价值，不只是“自动做事”，而是会先识别信息是否足够；如果不够，就优先补齐澄清，再进入开发。**

### 从这两个案例可以看出什么

把这两个真实调用过程放在一起看，可以更直观地理解当前 skill 的工作方式：

- **信息完整时**：它会快速结构化、快速规划、快速进入确认
- **信息不足时**：它会优先澄清关键变量，而不是直接实现
- **不论哪种情况**：它都会回到统一主链路，即“澄清 → 计划 → Gate 1 → 实现验证 → Gate 2 → 飞书图文交付 → 打包”

这也是当前 skill 相比多个分散 skill 最大的优势：它不是只有单点能力，而是始终围绕完整交付链来组织执行。

## 限制与注意事项

- 正式开发前必须经过 Gate 1 确认
- 最终交付前必须经过 Gate 2 验收
- 没有验证证据不能宣称完成
- 如果外部飞书权限或画板写入受限，会降级为本地交付包

## 常见问题

- **为什么这个 skill 要集成多个能力？**
  - 因为原始能力通常分散在多个 skill 中，真实使用时需要频繁切换，体验割裂；当前 skill 的价值就是把这些关键能力串成一个闭环。
- **它会自动生成飞书画板吗？**
  - 会。默认会生成介绍当前 skill 的画板，并给出插入文档的 action plan；如环境受限，则先输出本地 board spec 与命令计划。
- **是否还需要单独安装 design-lark-chart？**
  - 不需要。当前 skill 已经内置了轻量图表流水线和默认介绍板生成能力。
